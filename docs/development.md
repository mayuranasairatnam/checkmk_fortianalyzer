## Source layout, tests and reproducible package build

Sources live under `cmk_addons_plugins/fortianalyzer/`.
`cmk_addons/plugins` is a symlink to `../cmk_addons_plugins`, enabling local
imports through `cmk_addons.plugins.fortianalyzer`. Only `cmk_addons_plugins`
is packaged; the import symlink is excluded.

| File | Purpose |
| --- | --- |
| `libexec/agent_fortianalyzer` | HTTPS client, login/logout, API and optional SSH collection, and agent section output |
| `server_side_calls/fortianalyzer.py` | Builds the special-agent command from the host and rule settings, including password/token references |
| `rulesets/special_agent.py` | Connection settings, credentials, ADOM exclusions and optional SSH collection in Setup |
| `rulesets/check_parameters.py` | Configurable monitoring thresholds and units |
| `graphing/fortianalyzer.py` | Metrics, graphs and license perfometer |
| `agent_based/fortianalyzer.py` | Compatibility imports for checks compiled before the module split |
| `agent_based/fortianalyzer_api.py` | JSON parser and API status |
| `agent_based/fortianalyzer_system.py` | System identity and capacity |
| `agent_based/fortianalyzer_license.py` | Device license capacity and utilization |
| `agent_based/fortianalyzer_managed.py` | Logging device count |
| `agent_based/fortianalyzer_adoms.py` | ADOM and total log rates, including volume |
| `agent_based/fortianalyzer_support.py` | Support status and expiry |
| `agent_based/fortianalyzer_resources.py` | CPU, memory and disk |
| `agent_based/fortianalyzer_logvolume.py` | SSH volume validation and legacy volume checks |
| `lib/common.py` | Shared validation, numeric conversion and singleton discovery |

All checks continue to consume the shared `fortianalyzer` agent section.
Splitting the modules does not change service names or plugin IDs.

The data flow is: the Setup rule supplies connection settings and nested
authentication credentials, the server-side call starts the collector with a
secret reference, and the collector fetches data using the selected method.
Admin user logs in and out and optionally collects SSH volume; API user uses a
Bearer token and skips GUI/SSH. It then emits the `<<<fortianalyzer:sep(0)>>>`
JSON agent section, including the authentication method for service discovery.
The parser validates that section; the individual checks discover services and produce states and metrics.

From the project directory:

```sh
python3 -m pip install 'paramiko==4.0.0'
python3 -B -m unittest discover -s tests -v
python3 -B build_mkp.py
```

The offline tests require Paramiko for mocked SSH transports; no device
connections are made. They cover aggregation, real zeros, invalid and missing data,
partial rates, explicit ADOM exclusions, authentication, logout, GUI proxy
requests, Logview v3 responses, thresholds, license calculations, support,
memory units, SSH collection and deterministic package contents. They also
check unique plugin registration, the shared parser and inclusion of every
feature module and helper in the MKP. They also model both extended dictionary
constructors and verify that saved, empty and disabled exclusion lists remain
unchanged.

Without a local Checkmk installation, tests use API doubles. These do not
replace installation and discovery in a real site. Firmware-specific GUI
endpoints, memory units and account permissions must match the target appliance.
Package construction requires no external dependencies and excludes tests,
requirements notes and Python caches.

## CI and releases

GitHub Actions runs the offline tests and builds the MKP for pull requests and
pushes to `main`. After successful tests on `main`, CI creates a Git tag and a
GitHub Release with the matching MKP attached. The first release is `v1.0.0`
with `check_fortianalyzer-1.0.0.mkp`; subsequent releases increment the highest
stable tag's patch version (`v1.0.1`, `v1.0.2`, ...). Re-running a released
commit reuses its version. Non-release tags and prerelease tags are ignored.
The current workflow is triggered by pull requests and pushes to `main`;
it has no manual `workflow_dispatch` trigger.

The release job uses the automatic `GITHUB_TOKEN` with `contents: write`.
Download installable packages from the repository's
[GitHub Releases](https://github.com/mayuranasairatnam/checkmk_fortianalyzer/releases).

Local builds default to `1.0.2`. To build a specific release version:

```sh
python3 -B build_mkp.py --version 1.0.2
```

Generated MKPs are excluded from Git. Release notes are generated by GitHub.
Rerunning a released commit replaces its MKP asset with `--clobber`.
The workflow uses Python 3.12 and installs the test dependencies directly
before testing. Dependency versions are defined in `.github/workflows/ci.yml`.

For a standalone API test, the agent can read its password from stdin:

```sh
python3 cmk_addons_plugins/fortianalyzer/libexec/agent_fortianalyzer \
  --address faz.example.org --user monitoring --password-stdin
```

For a standalone API user test, read the token from stdin instead:

```sh
python3 cmk_addons_plugins/fortianalyzer/libexec/agent_fortianalyzer \
  --address faz.example.org --api-token-stdin
```

Supply the password or token through stdin for terminal tests. Use the Checkmk rule
for production operation.

## Form compatibility

New-rule prefill uses `ListExtended.prefill`. The outer `DictionaryExtended`
receives `default_checked` only when that field exists in
`DictionaryExtended.__dataclass_fields__` (Checkmk 2.5). With the Checkmk 2.4
constructor, no additional default parameters are passed.

The native special agent uses Agent-based API v2, Rulesets API v1,
Server-side Calls API v1 and Graphing API v1. The MKP metadata permits Checkmk
2.4.0 through 2.5.99; see [tested environments](../README.md#tested-environments)
for actual appliance/site validation.

Authentication tests are integrated into `tests/test_fortianalyzer.py`; release
version selection and package metadata tests live in `tests/test_release.py`.
Coverage includes default method selection, credential migration, safe secret
references, Bearer headers, skipped GUI/SSH queries and authentication-specific
service discovery. A sibling-project comparison can be skipped when its expected
local FortiManager project is unavailable; this is not a device integration test.
